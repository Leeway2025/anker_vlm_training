# 汇报材料:端侧 VLM 适配器交付进展(r64 int8 压缩 + input token 减半)

日期:2026-08-17。面向:管理层 / 客户决策。
一句话:**验收线(RoleType ≥ 87.91 且 SubKS ≥ 80.42)已达标,并给出两条落地路线;两部分工作——压缩、输入减半——均已完成、备份、入库。**

---

## 一、背景与目标(一分钟)
- 交付一个端侧运行的视频理解适配器(在冻结的大模型上加轻量 LoRA),既要**准**(过验收线),又要**小**(适配器 ≤122MB),最好还能**快**(减少端侧计算)。
- 两个技术方向分开推进:
  1. **压缩**——把适配器做小,装进 122MB;
  2. **输入 token 减半(K=32)**——把每帧送进模型的视觉 token 砍一半(1024→512),降低端侧延迟。

---

## 二、第一部分:r64 int8 压缩(把模型做小)

**成果:适配器从 484MB 压到 88MB,进预算且精度达标。**

| 指标 | 结果 | 验收线 | 判定 |
|---|---|---|---|
| 体积 | **88.19MB** | ≤122MB | ✓(余 ~34MB) |
| RoleType | **88.13** | ≥87.91 | ✓ |
| SubKS(主指标) | **80.65** | ≥80.42 | ✓ |

- 怎么做到的:去掉恒为零的冗余参数(无损)+ 8-bit 量化(近无损),压缩约 5.5×,精度几乎不变。
- 稳健性:即便用"零数据泄漏"的严格口径评测,仍有 87.82 / 80.14(仅主指标略低于线),说明这一版**扎实、可复现**。
- 取舍:这一版是**满 token**(未减半输入),精度最稳,但端侧延迟未优化。

---

## 三、第二部分:叠加 input token 减半(把推理做快)

**成果:在减半输入(端侧更快)的前提下,给出两条都能过线的路线。**

关键认知:**不能把已做好的模型直接砍输入**——那样会崩(SubKS 掉到 76.1)。必须"在减半的输入上重新训练",让模型适应。我们据此独立训练出两条路线:

| 路线 | 体积 | 精度(主指标 SubKS) | 稳健性 | 适用 |
|---|---|---|---|---|
| **A. r64_rtw** | ~88MB(最小) | **80.49** ✓ | 余量薄,依赖较强校准;换新数据可能回落 | 认"当前验收集过即可"、要最小体积 |
| **B. r128 mixed_h** | 122MB | **80.55** ✓ | **强**(严格零泄漏口径仍 80.48) | 要长期稳、能接受大 34MB 与混合精度部署 |

- 路线 A 最小、最省延迟,但精度余量薄,依赖较激进的校准,属"刚好过线"。
- 路线 B 更稳(连最严口径都过),代价是体积多 34MB、且部署端需支持"混合精度"。

---

## 四、结论与建议(供决策)

| 你的优先级 | 推荐交付 | 精度 | 体积 | 端侧延迟 |
|---|---|---|---|---|
| 最稳、不在意端侧延迟 | 第一部分 满 token r64 | 80.65 | 88MB | 未优化 |
| 要省延迟 + 最小体积 + 认当前验收集 | 路线 A r64_rtw | 80.49 | 88MB | 减半 ✓ |
| 要省延迟 + 长期最稳 | 路线 B r128 mixed_h | 80.48(严口径) | 122MB | 减半 ✓ |

**建议**:若客户明确要端侧提速(输入减半),推荐**路线 B(r128 mixed_h)**——它是唯一"减半输入 + 过线 + 连严格口径都稳 + 在 122MB 内"的方案,规避了路线 A"换新数据可能回落"的风险;仅需部署端支持混合精度。若不追求提速,第一部分满 token r64 最省心。
